## v1.1.0 — 2026-08-09

### Added

* `build --download-charts` puts every chart into `.nelmwave/charts/` and points the plan at it, so `up`, `down` and `diff` need nothing but the build directory — build where the charts are reachable, copy the directory over, apply in isolation. Remote charts are downloaded through the same helm getters nelm uses at apply time, so repository credentials, TLS material, plain-HTTP OCI and `provenanceStrategy` apply unchanged and a version constraint is resolved once; local charts are copied in as they are, with a relative path resolved from the manifest's directory like `values` and `stores`. Releases sharing a chart share one copy, the directory is rebuilt on every run, and a missing local chart fails the build rather than the apply. `up --build --download-charts` does both in one step (@zhilyaev)

### Changed

* `build` writes every artifact through an `os.Root` scoped to the build directory, so a `name:` from the manifest — or a symlink sitting in the directory — cannot land a file outside `.nelmwave/`, and a local chart is read through a root scoped to the chart, closing the symlink race between walking a directory and reading what the walk found (@zhilyaev)

## v1.0.0 — 2026-08-05

### Added

* A declarative manifest (`nelmwave.yml` or a gomplate-rendered `nelmwave.yml.tpl`) describing many Helm releases at once, applied through [nelm](https://github.com/werf/nelm) by four commands: `build`, `up`, `down` and `diff` (alias `plan`) (@zhilyaev)
* `build` is the only phase that renders anything: it writes a self-contained plan into `.nelmwave/` — `planfile.yml` plus resolved `values/<uniqname>/` and `stores/<uniqname>/` artifacts — and `up`, `down` and `diff` read that plan without re-rendering, so what was reviewed is what gets applied. `build` needs no cluster and downloads no charts, and the planfile is deterministic (map keys sorted) so it diffs cleanly in review (@zhilyaev)
* Manifest templating through [gomplate v5](https://gomplate.ca) with `[[ ]]` action delimiters, so Helm's own `{{ }}` passes through untouched. The render context exposes `.Env`/`getenv` and gomplate's standard namespaces (`strings`, `datasource`, `conv`, ...); a plain `nelmwave.yml` is loaded verbatim (@zhilyaev)
* Release identity as a **uniqname** map key — `name[@namespace[@kubecontext]]` — so a release body carries no `name`/`namespace` fields and equivalent spellings collapse to one release. Namespace and kube-context are optional and resolved at apply time. A free-form `project:` name is carried into the plan (@zhilyaev)
* `repositories`: a map keyed by helm-repo alias or OCI registry host, where the URL scheme decides how it is reached. Each entry takes `username`/`password`, `insecureSkipTLSVerify`, `passCredentials`, `caFile`, `certFile`/`keyFile` for mTLS, `skipUpdate` and a per-repository `requestTimeout`. There is no `repositories.yaml` step — helm charts are fetched `--repo` style and OCI credentials reach nelm through a generated temporary `config.json` (@zhilyaev)
* `oci+http://` as a repository scheme for registries without TLS. nelm accepts only `oci://`, so the reference is rewritten and the transport passed along separately — you never spell the scheme twice, and a chart addressed as `oci://registry:5000/api` still resolves against the `oci+http://` registry because the scheme is transport, not identity (@zhilyaev)
* Chart signature verification per repository: `provenanceStrategy` (`never`, `if-possible`, `always`, `later`) with `provenanceKeyring` for the public keys, defaulting to helm's `~/.gnupg/pubring.gpg`. OCI charts are matched to their registry by address prefix, longest first (@zhilyaev)
* `chart.name` accepts three forms — `alias/chart` resolved against a declared helm repository, an `oci://` (or `oci+http://`) reference, and a local chart path — with an optional `version` constraint (@zhilyaev)
* `values` and `stores`, both lists of file references resolved through a datasource layer: `values` become the release's values files in merge order, `stores` are companion files copied alongside them. Any gomplate scheme works (`env:`, `http(s)://`, `s3://`, `git://`, `vault://`, ...), four spellings are accepted (bare string or `src:` mapping, with or without a scheme), `name:` fixes the resolved artifact's name and `optional: true` skips a source that does not exist. Behaviour comes from the extension, not the scheme: `.yml` is copied verbatim, `.yml.tpl` rendered (@zhilyaev)
* In-process decryption of `.yml.sops` and `.yml.tpl.sops` sources — the `sops` binary is not required, and keys come from the ambient environment exactly as they do for the sops CLI (`SOPS_AGE_KEY_FILE`/`SOPS_AGE_KEY`, GnuPG, cloud KMS). The format handed to sops follows the extension underneath `.sops`, and `build` warns out loud whenever a run wrote decrypted material into `.nelmwave/` (@zhilyaev)
* Datasource cross-references: within a release `stores` resolve before `values`, and every resolved artifact is registered as a gomplate datasource (`stores/<name>`, `values/<name>`) visible to later artifacts of the same release. Resolution is backward-only, and a skipped `optional` source resolves to an empty placeholder instead of an error (@zhilyaev)
* `sets`: inline dotted-path value overrides applied on top of `values`, reaching nelm as type-preserving JSON — `3` stays a number and `false` stays a boolean, unlike `helm --set` (@zhilyaev)
* `needs`: dependency edges combining explicit `needs.releases` entries with an inlined label selector (`matchLabels`, `matchLabelsExpressions`). A named dependency is required by default and `optional: true` downgrades it to a warning; label-matched dependencies are always optional, an empty selector matches nothing, and cycles are rejected at build time with the cycle printed (@zhilyaev)
* A concurrent dependency-DAG executor: independent releases are applied in parallel under `--concurrency`, a failure stops only its own branch while unrelated branches keep running, and `down` reverses every edge so dependents are removed before what they depend on (@zhilyaev)
* `labels` on releases, used for `-l/--selector` selection and label-based `needs`, with values coerced to strings. The same labels are written onto the release's storage object, so `kubectl get secret -l app=api` finds it in the cluster; helm's own `name`, `owner`, `status` and `version` are applied afterwards and win (@zhilyaev)
* `annotations` on releases, stored with each revision and read back with `nelm release get` — values a label cannot hold (URLs, commit messages, e-mail addresses), deep-merged with the `Release:` block so per-release entries add to the common ones (@zhilyaev)
* A `namespace` block per release covering `create` (default `true`), `delete` (default `false`), and `labels`/`annotations` merged onto the namespace object. Metadata is applied **before** the release, so a policy label such as `istio-injection` or `pod-security.kubernetes.io/enforce` is in place before any workload is created; with `create: false` an existing namespace is patched rather than created behind your back, `down` warns for every release carrying `delete`, and writing `namespace: production` as a string is an error rather than a silent no-op (@zhilyaev)
* Per-release `timeout` bounding the operation and `autoRollback` rolling back to the last deployed revision on failure (helm's `--atomic`) (@zhilyaev)
* Resource policies per release: `forceAdoption` to take over resources another helm release claims, `removeManualChanges` (default `true`) to reclaim hand-edited fields, `installCRDs` (default `true`) for the chart's `crds/` directory, `deletePropagation` (`Foreground`/`Background`/`Orphan`, validated at build time) and `historyLimit` (default `10`). `deletePropagation` and `historyLimit` apply to `down` too, and `removeManualChanges` applies to `diff` so the preview matches the apply (@zhilyaev)
* `driverURL` selecting where release state lives: `kubernetes://secrets` (the default), `kubernetes://configmaps`, or PostgreSQL via `psql://user@host:5432/db`. Leave the password out and let libpq read `PGPASSWORD`: `build` warns if it finds one embedded, since the manifest is copied into `planfile.yml` in cleartext (@zhilyaev)
* Top-level `Release:` and `Namespace:` blocks as type defaults applied to every release: maps deep-merge with a release's own keys winning, lists are replaced rather than merged (@zhilyaev)
* `-l/--selector` with Kubernetes-style label selectors (`app=api,env in (prod,stg),tier!=db`), and `--include-needs` widening the selection along the graph in the direction the command travels: dependencies for `up` and `diff`, dependents for `down`. Without it `up` refuses to run when a required dependency is filtered out. Every run logs the final selection, and anything the selector did not name is called out as a warning (@zhilyaev)
* Switches for how much `diff` prints: `--no-verbose-diffs`, `--show-verbose-crd-diffs`, `--show-insignificant-diffs`, `--show-sensitive-diffs` and `--diff-context-lines`. `diff --detailed-exitcode` reports planned changes as exit code 2 without being a failure, and `up --dry-run` always plans with the default view (@zhilyaev)
* Cluster connection entirely through flags, never manifest fields, so no credential is copied into the build artifacts: a repeatable `--kube-config` that merges like `KUBECONFIG=a:b` (earlier wins, as kubectl does), `--kube-context` for releases whose uniqname names none, direct connection without a kubeconfig (`--kube-api-server`, `--kube-token[-path]`, `--kube-ca[-data]`, ...), client certificates and basic auth, impersonation (`--kube-impersonate-user`, ...) and client-side throttling (`--kube-qps-limit`, `--kube-burst-limit`, `--kube-request-timeout`). nelmwave's own namespace calls use the same connection, so metadata and workloads cannot land in different clusters (@zhilyaev)
* `nelmwave completion` for bash, zsh, fish and powershell, completing values as well as names: label keys and their values from the built plan behind `-l`, kube-contexts from the kubeconfig, the accepted `--log-level`/`--log-format` values, and manifests behind `--file`/`--output`. The commands take no positional arguments, so nothing irrelevant is offered (@zhilyaev)
* Logging controlled by `--log-level` (debug/info/warn/error, which also sets nelm's own verbosity) and `--log-format`, where `auto` picks console output on a TTY and JSON everywhere else so CI logs stay machine-readable without a flag (@zhilyaev)
* A runnable `examples/` project per feature area — dependencies, chart sources, namespaces, resource policies, release storage, sops-encrypted values, datasource cross-references and running in CI — all built by `make examples`, plus an asciicast of the full loop in `demo/` (@zhilyaev)
* An end-to-end suite driving the real command tree against a real Kubernetes API (build, up, a clean diff, a drifting diff with exit code 2, the upgrade that resolves it, a selective down, a full down, the needs policy). The cluster is a k3s container owned by docker-compose, the suite sits behind the `e2e` build tag so `go test ./...` never reaches for a cluster, and it installs a local chart from `testdata` so nothing is downloaded (@zhilyaev)
* GitHub Actions CI — lint, race-enabled tests on Linux and macOS, example builds, an e2e run against the k3s fixture, govulncheck and gosec — plus a changie-driven goreleaser release pipeline publishing binaries, a ghcr.io image and a Homebrew formula (@zhilyaev)
* Every flag can now be set through an environment variable — uppercase the flag, swap `-` for `_`, prefix with `NELMWAVE_` (`NELMWAVE_LOG_LEVEL`, `NELMWAVE_KUBE_CONTEXT`, ...). Precedence is flag, then variable, then default, and `--help` prints the variable next to each flag (@zhilyaev)
